What it takes to read a clock

A convolutional net reads a 12-hour analog dial to the nearest five minutes with near-perfect accuracy — and the interesting part is everything that had to be checked before that number could be trusted.

The task

144 buckets on a 12-hour face

Every five-minute position on a 12-hour dial is one class: 12-00, 12-05, … 11-55. 144 of them. The training data is 14,400 rendered clock faces — clean line art, upright, centered, hands on exact marks — split 80 / 10 / 10. The backbone is an EfficientNet‑B3 fine-tuned from ImageNet; the head is a flat 144-way softmax.

The first lesson had nothing to do with vision. The classes were loaded from a CSV column of labels like 10_05, and the model's output order followed a plain alphabetical sort of those strings — where _ sorts after the digits. Sort the hyphenated folder names instead (- sorts before digits) and every prediction shifts by whole hours: a silent ~33-point accuracy loss from code that runs without complaint. It is now pinned by a test that fails against both wrong orderings.

Two defects in the synthetic renderer account for nearly every remaining error. Some dials are drawn blank — no hands at all — so the true time is unknowable from the image. Others have both hands drawn exactly ±3h15m from the folder's labelled time. Netting those out, the model's real error rate on this data is about 0.03%.

How the defects were told apart from genuine model error

Grad-CAM. On a correct prediction the attention sits tightly on the hand tips. On the ±3h15m images it still sits on the hand tips, confidently — the model is reading the hands that were actually drawn; the label is what's wrong. The blank-dial images produce diffuse, low-confidence attention with nothing to latch onto. Those two signatures — confident-but-wrong and diffuse-and-unsure — are now a script (flag_suspects.py) that auto-surfaces suspect images in any dataset built the same way, instead of diagnosing class by class. Run over all 14,400 images it flags every one of the model's 26 misreads: 24 blank dials (all the same filename in each class folder, confidence pinned near 0.08) and 2 hand-shift images, both landing exactly ±195 minutes off.

Robustness

Brittle to rotation, until the training range said otherwise

The model reads the printed numerals, not absolute hand geometry — its predictions are exactly invariant to 90°, 180° and 270° rotation. But tilt a dial just a few degrees and accuracy fell off a cliff into a confident, wrong dead zone. Every training image is perfectly upright, so this was never exercised.

Sweeping test-time rotation across checkpoints trained with different augmentation ranges showed the rule exactly: each model stays accurate across roughly its literal training rotation range, and no further. Widening the augmentation widens the safe band one-for-one — at no cost to upright accuracy.

The ±54° model is robust across the entire ±90° sweep and posts the best upright accuracy of any checkpoint (99.82%). It is now the default. A cyclic sin/cos regression head was also tried, to respect that 11:55 and 12:00 are neighbours; it failed, because the same rotation augmentation that helps a classifier corrupts an absolute-angle regression target.

The limit

Real photographs are a different problem

On 92 real clock photos — angles, glare, odd typefaces, hands between marks — the synthetic model scores about 2%. That is not a tuning gap. Rotation robustness was ruled out (the ±54° model does no better). Adding heavy photometric and perspective augmentation to the synthetic renders did nothing: the augmented images still don't look like photographs.

What moved the needle was real data. Folding 138 labelled real photos into training and fine-tuning from the synthetic checkpoint roughly tripled held-out real accuracy and halved the median error, while synthetic accuracy held.

Still not usable. 19% is a direction, not a destination. The bottleneck now is plainly data volume — 195 labelled real photos across 99 of 144 classes, with the model overfitting to the common times in that small set. The next lever is more real photographs or a photorealistic renderer, not more training tricks.

Can you at least tell when to trust it?

On the synthetic data, yes — the model is already well calibrated (expected calibration error 0.002), so a confidence threshold cleanly separates safe predictions from risky ones. On real photos the synthetic-only model's confidence is anti-informative: its most confident real predictions are its least accurate. Fine-tuning on real data repairs the ranking — the top ~12% of real predictions by confidence are ~86% correct — even though the absolute numbers stay overconfident. Temperature scaling can't close that gap; it's domain shift, not a scaling error.

Method

Trusting the numbers

Both of the worst bugs in this project — the class ordering, the rotation-augmented regression target — produced plausible code that ran cleanly and was quietly wrong. So every change that touches labels, preprocessing or model loading is checked against a fixed test-split number and a unit-test tier that locks in both known-wrong class orderings. Headline accuracy is always reported twice: the raw number, and the number with the catalogued dataset defects removed. A result that only exists in a training log is not a result.
